La capa de runtime de `@nekzus/liop` coordina la detección de topología de red, el enrutamiento dinámico a través de transportes heterogéneos y el ciclo de vida de la autenticación máquina a máquina (M2M).

Garantiza que, independientemente de si un agente se ejecuta en un entorno de desarrollo local, un proxy perimetral o una malla distribuida de alta seguridad, las peticiones se enruten a través del canal más eficiente y seguro disponible.

## Descubrimiento Adaptativo de Red (`TopologyProbe`)

En lugar de requerir que los operadores configuren manualmente endpoints, multiaddrs y URLs de descubrimiento OIDC, `TopologyProbe` implementa autodescubrimiento mediante una única URL en conformidad con **RFC 9728 (OAuth 2.0 Protected Resource Metadata)**, **RFC 8414** y **NIST SP 800-207 (Arquitectura Zero Trust)**.

```typescript
import { probeTopology, type TopologyProbeOptions } from "@nekzus/liop";

const options: TopologyProbeOptions = {
  blgUrl: "http://127.0.0.1:15018",      // URL explícita del Border LIO Gateway
  nexusUrl: "http://127.0.0.1:15000",    // Proveedor OIDC Nexus
  clientId: "mesh-diagnostic-agent",
  clientSecret: process.env.LIOP_CLIENT_SECRET,
  bootstrapNodes: [                      // Multiaddrs opcionales de la DHT P2P
    "/ip4/127.0.0.1/tcp/15001/p2p/12D3KooW..."
  ]
};

const topology = await probeTopology(options);
console.log(`Modo Determinado: ${topology.mode}`); // "gateway" | "mesh" | "hybrid"
```

### Flujo de Descubrimiento

1. **Sonda de Recurso Protegido RFC 9728**: Consulta `/.well-known/oauth-protected-resource` y `/health` en las URLs candidatas.
2. **Encadenamiento de Metadatos**: Extrae automáticamente el `issuer` del servidor de autorización, el `token_endpoint`, los `scopes` soportados y las herramientas (`tools`) publicadas.
3. **Normalización del Puente de Red**: En entornos de desarrollo híbridos Docker-to-Host, los nombres de host internos de contenedores (`nexus-prod`, `172.20.0.x`) se traducen de forma segura a los puertos publicados del host (`127.0.0.1:15000`).
4. **Resolución del Modo de Ejecución**:
   - **`gateway`**: Detectado cuando un Border LIO Gateway saludable responde y no se configuran nodos bootstrap P2P. Minimiza el consumo de recursos operando exclusivamente sobre HTTP/JSON-RPC sin levantar hilos de red libp2p.
   - **`mesh`**: Activado cuando solo se proporcionan nodos bootstrap P2P DHT. Opera de forma soberana sobre gRPC con cifrado Noise y post-cuántico Kyber768.
   - **`hybrid`**: Activado cuando se detectan tanto endpoints de gateway como nodos bootstrap de malla. Enruta herramientas perimétricas a través del gateway mientras ejecuta cómputo en enclaves directamente sobre pares de la malla.

## Enrutamiento Híbrido por Herramienta (`RoutingTable`)

En despliegues empresariales distribuidos, distintas capacidades demandan diferentes protocolos de transporte. Por ejemplo, las sondas de diagnóstico se ejecutan localmente, las herramientas de indexación pública se enrutan mediante gateways perimétricos y las consultas a libros contables confidenciales exigen canales soberanos gRPC directos.

`RoutingTable` gestiona la resolución de rutas por herramienta, la telemetría de latencia y la tolerancia a fallos automática.

```typescript
import { RoutingTable, type ToolDefinition } from "@nekzus/liop";

const table = new RoutingTable();

// 1. Registrar herramientas expuestas por un HTTP Gateway
table.registerGatewayTools(
  [{ name: "SearchIndex", description: "Consulta a índice vectorial público" }],
  "http://127.0.0.1:15018/mcp",
  true // authRequired
);

// 2. Registrar herramientas descubiertas sobre la malla P2P
table.registerMeshTools(
  [{ name: "BankAnalytics", description: "Agregación de saldos en enclave" }],
  "127.0.0.1:15021", // Destino gRPC
  false // autenticación interna de malla
);

// 3. Registrar herramientas de diagnóstico en proceso
table.registerLocalTool({
  name: "LiopMeshStatus",
  description: "Telemetría instantánea del nodo"
});

// Resolver ruta óptima
const route = table.resolve("BankAnalytics");
console.log(`Proveedor de ruta: ${route?.provider}`); // "p2p-grpc"
```

### Proveedores de Transporte

| Proveedor | Protocolo de Transporte | Caso de Uso Típico |
|---|---|---|
| `http-gateway` | HTTP/1.1 o gRPC-Web vía MCP JSON-RPC | APIs perimétricas, proxies inversos y microservicios de borde |
| `p2p-grpc` | libp2p directo + HTTP/2 gRPC con PQC Kyber768 | Enclaves soberanos Tier 1 (`Bank`, `Vault`) que requieren ZK-Receipts |
| `local` | Manejador sincrónico en proceso | Herramientas de diagnóstico, reporte de estado y health checks |

### Disyuntor (Circuit Breaker) y Resiliencia

`RoutingTable` monitoriza la fiabilidad de ejecución por herramienta:

- **`recordSuccess(toolName, latencyMs)`**: Restablece los contadores de fallos consecutivos y almacena la latencia instantánea para optimizaciones de reparto de carga.
- **`recordFailure(toolName)`**: Incrementa el contador de fallos. Cuando una ruta alcanza **5 fallos consecutivos** (`MAX_FAILURES = 5`), el disyuntor se activa (*tripped*), emitiendo una advertencia y permitiendo que los despachadores alternativos omitan endpoints degradados.
- **`getAllToolDefinitions()`**: Exporta la lista de todas las herramientas activas ordenadas alfabéticamente para cumplir con el requisito del protocolo MCP en `tools/list`.

## Ciclo de Vida de Tokens M2M (`TokenManager`)

La clase `TokenManager` administra el ciclo de vida de tokens Bearer máquina a máquina (M2M) bajo **OAuth 2.1 (RFC 6749, RFC 8707 Resource Indicators, RFC 9068 Perfil JWT)**.

```typescript
import { TokenManager } from "@nekzus/liop";

const tokenManager = new TokenManager({
  tokenEndpoint: "http://127.0.0.1:15000/oidc/token",
  clientId: "border-gateway-client",
  clientSecret: process.env.LIOP_CLIENT_SECRET!,
  audience: "urn:liop:mesh:api",
  scopes: ["liop:tools:call", "liop:mesh:query"]
});

// Obtiene el token en caché o solicita uno nuevo
const token = await tokenManager.getToken();
```

### Refresco Preventivo y Desduplicación de Concurrencia

Para soportar cargas analíticas masivas y de alta frecuencia sin sufrir fallos transitorios de autenticación, `TokenManager` implementa dos patrones fundamentales:

1. **Margen Preventivo de Refresco (`REFRESH_BUFFER_MS = 30_000`)**: Si a un token de acceso le quedan menos de 30 segundos de vida útil, `TokenManager` dispara automáticamente su renovación *antes* de despachar la petición. Esto elimina condiciones de carrera HTTP 401 Unauthorized durante la ejecución de scripts WASI prolongados.
2. **Desduplicación de Peticiones en Vuelo**: Cuando múltiples llamadas asíncronas a herramientas solicitan un token simultáneamente con la caché vacía, `TokenManager` las unifica en una única petición HTTP POST en vuelo (`pendingPromise`). Todos los llamadores concurrentes resuelven contra la misma respuesta de red, impidiendo la saturación de cuotas en el servidor OIDC.

### Invalidación Reactiva

Si un enclave superior revoca una clave de acceso o rota certificados de firma, el gateway cliente invalida el token obsoleto de inmediato:

```typescript
try {
  await dispatchRpc(route, payload, await tokenManager.getToken());
} catch (error) {
  if (isHttp401(error)) {
    // Purga el token en caché para que el siguiente intento adquiera uno nuevo
    tokenManager.invalidate();
    return await dispatchRpc(route, payload, await tokenManager.getToken());
  }
  throw error;
}
```
